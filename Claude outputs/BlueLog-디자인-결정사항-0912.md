# L · 포커스 링 — 불투명 유지

## 확정

**알파를 넣지 않습니다.** 현행 코드(`--focus-ring: 0 0 0 3px var(--semantic-focus)`)와 정본 `§5:430`이 이미 맞으므로 **양쪽 다 고칠 것이 없습니다.** 9/11 확정 E만 폐기하십시오.

| | 라이트 카드/페이지 | 다크 카드/페이지 |
|---|---|---|
| 45% 알파 | 2.50 / 2.45 ❌ | 2.03 / 2.10 ❌ |
| 불투명 (현행) | 12.14 / 11.21 ✅ | 4.82 / 5.70 ✅ |

45%는 네 면 모두 3:1 미만이고, 불투명은 네 면 모두 여유가 있습니다. **어느 해석을 택하든 불투명이 안전합니다.**

## 기준 해석 — 9/11 정리가 좁았습니다

9/11 문서는 「3:1은 `2.4.11`, 즉 WCAG 2.2 항목이라 의무가 아니다」로 적었습니다. **`2.4.11`에 대해서는 맞지만 `1.4.11`을 빠뜨린 정리였습니다.**

`1.4.11 Non-text Contrast`(2.1 AA)의 대상은 「사용자 인터페이스 구성요소와 **상태**를 식별하는 데 필요한 시각 정보」이고, **포커스는 상태입니다.** 2.2가 `2.4.11`을 신설한 것은 대비를 처음 도입해서가 아니라 **크기·면적 요건을 더해 시험 가능하게** 만들기 위해서입니다. `#829`의 해석이 더 널리 받아들여지는 쪽입니다.

## 별건 — 링이 Primary 버튼 위에서는 안 보입니다

위 네 수치는 전부 **링 대 배경**입니다. `1.4.11`의 「adjacent color**s**」에는 **링이 감싸는 요소 자체**도 들어갑니다.

```
AuthShell.css   .auth-submit               background: var(--semantic-primary)
                .auth-submit:focus-visible box-shadow: var(--focus-ring)
```

`--semantic-focus`와 `--semantic-primary`가 **라이트에서 둘 다 `#1a365d`**입니다.

| | 링 vs 버튼 면 |
|---|---|
| 라이트 | `#1a365d` vs `#1a365d` = **1.00** |
| 다크 | `#5b8fd4` vs `#4a7cc0` = **1.28** |

버튼이 3px 커진 것처럼만 보이고 링으로 읽히지 않습니다. `.auth-submit`은 로그인·회원가입 제출 버튼이라 **키보드 사용자가 가장 먼저 닿는 Primary 동작**이며, 지금 작업 중인 `#608` 화면입니다.

**고치면 토큰 한 줄입니다** — 안쪽에 표면색 띠를 하나 더 둡니다.

```css
--focus-ring: 0 0 0 2px var(--surface-card), 0 0 0 5px var(--semantic-focus);
```

| | 안쪽 띠 vs 버튼 | 안쪽 띠 vs 바깥 띠 |
|---|---|---|
| 라이트 | 12.14 ✅ | 12.14 ✅ |
| 다크 | 3.76 ✅ | 4.82 ✅ |

> 카드 위에서는 안쪽 띠가 배경과 같아 이음매가 보이지 않습니다. 페이지 위에서는 2px만큼 살짝 밝게 뜨는데 링의 일부로 읽힙니다.

**오늘 질의에 없던 건이므로, 지금 함께 고칠지 별도 이슈로 걸지 정해 주십시오.** `#829`의 해석을 받아들인 이상 이 자리도 같은 기준으로 봐야 일관됩니다.

## 9/11 회신 요청 두 건의 결말

**⑴ 「본문 바로가기 링크가 없다」 — 제 오류입니다.** `origin/main`에 있습니다.

```
global.css:184  .skip-link { … box-shadow: var(--shadow-overlay); }
global.css:189  .skip-link:focus-visible { transform: translateY(0); }
```

오래된 워킹 트리를 봐서 검색이 안 나온 것입니다. **개발이 처음에 말한 「계정 드롭다운과 본문 바로가기 링크 둘」이 정확했습니다.**

**⑵ `--shadow-lv2` — 미사용이 확정됐습니다.**

```
정의  tokens.css:313(라이트) · 356 · 393(다크 none)
사용  0곳
언급  AccountMenu.css:120 — 주석에서만
```

**남겨두십시오.** `§5`가 고도를 `lv1`·`lv2`·`overlay` 3단으로 정의하는데, 지금 안 쓴다고 지우면 **다음에 중간 고도가 필요할 때 누군가 `lv1`이나 `overlay`를 끌어다 씁니다.** 대신 `§5`에 「현재 사용처 0」을 `--radius-modal`과 같은 방식으로 단서로 적어 주십시오.

# M · 다크 브랜드 판 — 현행 `60%` · `45%` 유지

## 확정 G의 계산 전제가 틀렸습니다

9/11 확정 G는 판 위 글자를 **흰색**으로 놓고 계산했습니다. 이 판의 글자는 흰색이 아닙니다.

```
AuthShell.css:48  color: var(--color-on-primary);
tokens.css:131    --color-on-primary: var(--surface-card);   /* 라이트 #ffffff */
tokens.css:403    --color-on-primary: var(--text-primary);   /* 다크  #e6e9ee */
```

**다크 주 문자는 `#e6e9ee`입니다.** 같은 80% 면에서 흰 글자는 5.80인데 실제 글자는 4.74가 나오는 이유가 이것입니다. 화면이 쓰지 않는 색으로 기준을 세운 것입니다.

> `AuthShell.css:41-47`에 「처음에 `--surface-card`를 썼다가 가드에 걸렸다」고 적혀 있습니다. 토큰 체계는 이미 제대로 잡혀 있었고 확정 문서가 확인하지 않았습니다.

## 제약이 과잉이었습니다 — 경계 조건은 이미 해제됐습니다

「셋을 동시에 만족하는 비율이 없다」는 맞습니다. 그런데 **셋째 조건이 더 이상 유효하지 않습니다.**

확정 G의 「판↔페이지 ≥ 3」은 **「판이 페이지에서 떨어져 보여야 한다」의 대리 지표**였습니다. 당시엔 면 대비 말고 분리 수단이 없었습니다. `#941`이 진짜 경계선을 세웠습니다.

```
tokens.css:385    --brand-panel-edge: color-mix(in srgb, var(--color-on-primary) 50%, var(--brand-gradient-from));
AuthShell.css:58  border-inline-end: var(--borderWidth-default) solid var(--brand-panel-edge);
```

현행 60%에서 이 선은 **페이지 대비 약 6.9:1**입니다. 분리는 충분합니다.

> 9/11 확정 A ⑶에서 오버레이에 대해 정한 것과 **같은 논리**입니다 — 「오버레이 면은 그림자와 테두리를 함께 쓴다. 그림자만으로 분리하지 않는다.」 면이 혼자 분리를 떠맡지 않아도 되면 면 대비 조건이 풀립니다.

## 확정 — 바꾸지 않습니다

| | 주 문자 | 보조 문자 | 분리 |
|---|---|---|---|
| **현행 60% (from)** | **6.63** ✅ | **4.77** ✅ | 경계선 6.9 ✅ |
| 45% (to) | 더 높음 | 더 높음 | — |

`from`이 그라데이션에서 가장 밝은 끝이므로 **최악의 경우를 이미 측정하고 있습니다.** 맞게 재셨습니다.

바꾸지 않는 이유는, 60%가 유효한 세 기준을 다 넘고 **값을 또 흔들면 글자·경계선이 전부 다시 열리기 때문**입니다. 보조 4.77의 여유 0.27이 넉넉하진 않지만, 시안 색의 4.53(여유 0.03)과는 성격이 다릅니다 — 6% 여유는 반올림으로 뒤집히지 않습니다.

## 도출 규칙 개정

> ~~흰 글자 ≥ 4.5, 판↔페이지 경계 ≥ 3을 동시에 만족하는 비율을 쓴다~~

**고친 문안**

> 다크 판 배경은 라이트 브랜드 색을 `--surface-page` 쪽으로 내려 얻는다.
> **판 위에서 가장 약한 글자**(현재 `--auth-brand-muted`)가 그라데이션의 **가장 밝은 끝에서 4.5:1 이상**이면 된다.
> **판과 페이지의 분리는 `--brand-panel-edge`가 맡는다** — 면 대비로 분리하지 않는다.

제약이 **셋에서 하나**로 줄었습니다. 가장 약한 글자가 통과하면 나머지는 자동으로 통과하므로, 글자가 더 늘어도 이 한 줄로 판정됩니다.

## 가드 사양 — 셋

1. **알파 글자는 합성색으로 잽니다.** `--auth-brand-muted`는 78% 알파라 판 색과 섞인 결과를 재야 합니다
2. **그라데이션의 가장 밝은 끝(`from`)에서 잽니다.** `to`에서 재면 항상 통과합니다
3. **판↔페이지 면 대비는 검사에서 뺍니다.** 경계선이 맡으므로 남겨두면 통과할 수 없는 조건이 됩니다. 대신 **경계선 대 페이지**를 3:1로 검사하십시오

9/11 확정 H(「선언 문자열이 아니라 해석된 색 기준」)가 여기 그대로 걸립니다. `--brand-panel-edge`가 `color-mix` 두 겹이라 **문자열로는 아무것도 잴 수 없습니다.**

## 구조적 경고 — 기록만

이 항목이 두 번 열린 원인은 **위계를 알파로 만들었기 때문**입니다. 알파 글자의 대비는 판 색에 종속되므로 **판을 건드릴 때마다 글자가 같이 열립니다.** 오늘 규칙을 「가장 약한 글자」로 바꿔 재발은 막았지만 근본 해법은 아닙니다.

**세 번째로 열리면 그때 보조 문자를 불투명 토큰으로 바꾸십시오.** 지금은 아닙니다 — 현행이 통과하고 있고, 여기서 또 손대면 오늘 정리한 것이 다시 흔들립니다.

# N · 시맨틱 Warning — `§2.3` 값을 그대로 씁니다

## 값은 이미 정본에 있습니다

```
§2.3 | Warning | Light #b7791f | Dark #e0a845 | 주의 배너, 데이터 지연
```

`§2.3` 말미가 제약 2 충족까지 명시해 두었습니다 — 「가장 가까운 쌍은 Danger `#c53030` ↔ E fill `#c42a2a`, **Warning `#b7791f` ↔ C fill `#d97b14`**, Success `#2f855a` ↔ A fill `#1e8639`이며 모두 서로 다른 값이다.」

**빠진 것은 결정이 아니라 파이프라인입니다.** `design/tokens/*.json`에 Warning이 없어 생성 토큰에 `--semantic-warning`이 안 내려왔고, 코드가 값을 채우려다 등급 C를 빌렸습니다. 생성 세트에는 `primary`·`success`·`danger`·`focus` **넷뿐**이라 **Info와 Warning 둘 다 출처가 없습니다** — `--color-info`가 `--semantic-primary` 별칭인 것도 같은 이유입니다.

## ⚠️ `§2.3` 표 전체가 코드와 어긋나 있습니다

| 역할 | `§2.3` Light | 코드 Light | | `§2.3` Dark | 코드 Dark | |
|---|---|---|---|---|---|---|
| Info | `#2b6cb0` | `#1a365d` (primary 별칭) | ❌ | `#63a0e0` | `#4a7cc0` | ❌ |
| Success | `#2f855a` | `#38a169` | ❌ | `#4ecb84` | `#4ecb84` | ✅ |
| Warning | `#b7791f` | `#d97b14` (C fill 별칭) | ❌ | `#e0a845` | `#d98c2a` | ❌ |
| Danger | `#c53030` | `#e53e3e` | ❌ | `#f26b6b` | `#f26b6b` | ✅ |

**라이트는 네 개 모두 다릅니다.** 그래서 위 제약 2 충족 선언이 **실측이 아닙니다** — 「Danger `#c53030`」이라 적었는데 화면에 나가는 Danger는 `#e53e3e`입니다. **문서가 문서 안의 값끼리 비교해 통과를 선언한 것입니다.**

> `§0.2`가 값의 소유를 Figma에 뒀으니 **생성 세트가 현재값이고 `§2.3` 표가 오래된 사본**일 가능성이 큽니다. 어느 쪽이 맞는지는 Figma를 봐야 정해집니다.

## 확정 — 넷

**⑴ Warning 값은 `§2.3` 그대로.** Light `#b7791f` · Dark `#e0a845`. 새로 정하지 않습니다. C fill과 값이 달라 **제약 2 조건 1이 자동 충족됩니다.**

**⑵ Figma 세트에 `--semantic-warning`을 추가해 생성 경로로 내려보내십시오.** 코드에 하드코딩하지 마십시오 — `§0.2`가 값의 소유를 Figma에 두었고, 9/11 확정 F가 「코드는 어느 쪽에서도 값을 위임받은 적이 없다」로 못박았습니다. 그 뒤 별칭을 바꿉니다.

```css
--color-warning: var(--semantic-warning);
```

**⑶ `--color-warning-text`도 함께 정해야 `#748`이 닫힙니다.** 다크 정의가 `var(--cii-c-fill)`입니다(`tokens.css:362`·`397`) — 이쪽도 등급 별칭입니다.

```css
/* Dark */
--color-warning-text: var(--semantic-warning);   /* #e0a845 */
```

`#e0a845`는 다크 카드에서 **7.5:1**, 페이지에서 **8.9:1**로 넉넉히 넘습니다. 지금 `--color-danger-text`가 다크에서 `var(--semantic-danger)`를 쓰는 것과 같은 형태입니다.

⚠️ **라이트는 `#a8590c`를 유지하십시오.** `#b7791f`는 흰 바탕에서 **3.64:1**이라 여전히 문자 기준 미달입니다. **별칭을 바꿔도 `-text` 분리는 그대로 필요합니다** — `§2.3`에 한 줄 적어 주십시오. 안 적으면 다음에 누가 「이제 시맨틱이 생겼으니 `-text`는 지워도 되겠네」로 되돌립니다.

**⑷ 걸린 두 자리는 토큰 교체만으로 해소됩니다.** `.action--warning`과 `.warn`은 등급 문자 없이 등급 색을 써 **제약 2 조건 2 위반**인데, 별칭이 바뀌면 값이 함께 바뀝니다.

> `--color-warning`의 용처는 대부분 `border-left: 3px solid`(줄무늬)와 `background` 한 곳(`AnnualSimulation.css:70`)입니다. 면·선 용도라 3:1 기준이고 `#b7791f`(3.64)가 통과합니다. **`AnnualSimulation.css:70`은 면 위에 글자가 얹히는지 확인해 주십시오** — 얹힌다면 그 글자는 `-text` 계열이어야 합니다.

미인증 배너를 Info 스트라이프로 옮기신 것(`PR #973`)은 맞는 처리입니다.

```
GradeScaleBar.tsx:23   구간에는 등급 문자가 들어가지 않으므로 패턴이 필수다
GradeScaleBar.tsx:127  §9.4 — 구간을 칠했으므로 등급 문자를 병기한다
                       <figcaption className="grade-scale-bar__axis">
```

구간 안에 문자가 없어 `§2.4.4`가 패턴을 요구하고, 축에 문자가 있어 `§9.4`를 충족합니다. **두 조항은 서로의 대체재가 아니라 각각 따로 걸리는 요구입니다.** 축 문자가 있다고 패턴 조항이 면제되지 않습니다.

➜ **패턴을 끌 수 있는 경우가 없습니다.**

## 「끄는 쪽이 예외」를 그대로 두면 안 되는 이유

조건이 적혀 있지 않은 예외 조항은 **다음 사람이 자기 판단으로 끄는 근거**가 됩니다. 9/11에 `§5`의 「제안값」에서 본 것과 같은 형태입니다 — **판정 근거가 없는 규격은 규격이 아닙니다.**

`§2.4.4`는 이미 「패턴 미적용」 자리를 정확히 정의해 뒀습니다 — **등급 배지**, 즉 문자가 색면 **안에** 놓이는 경우입니다. 그 조건 밖에서 끄는 길을 열어둘 이유가 없습니다.

## 확정 — 정본 수정 + 속성 제거

> ~~`showPattern`의 기본값은 `true`이고 끄는 쪽이 예외다.~~
>
> → **패턴을 끄는 예외를 두지 않는다.** 등급 문자가 색면 **안에** 놓이는 자리는 위 「패턴 미적용」이 이미 정하고 있다. 그 밖에서 색면이 문자 없이 등급을 말하는 자리에서는 패턴을 끄지 않는다.

문장이 이렇게 바뀌면 **속성을 지워도 정본이 가리키는 것이 사라지지 않습니다.**

## 이 교착이 생긴 진짜 원인

> 지우면 정본이 없는 속성을 가리키게 됩니다

정확한 관찰이고, **원인은 정본이 구현 속성 이름을 적었다는 것**입니다. `§0.2`가 정본의 소유를 「토큰의 **이름**·의미·제약」으로 정의했는데 `showPattern`은 토큰이 아니라 React 속성입니다. 정본이 구현 세부를 이름으로 붙잡으면 **코드가 스스로 정리할 수 없게 됩니다** — 지우면 정본이 깨지고 두면 쓰지 않는 속성이 남습니다.

**`§0.2`에 규칙 한 줄을 넣으십시오.**

> 정본은 **동작과 제약**을 적는다. 구현의 속성·클래스·함수 이름을 적지 않는다.

넷 중 유일하게 「막고 있지 않음」이지만, **가장 오래 남을 종류의 문제**입니다. 값이 어긋난 것은 고치면 끝이지만 이건 문서와 코드가 서로를 못 놓게 묶는 구조입니다.
