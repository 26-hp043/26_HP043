# A · `--shadow-overlay` 값

## 확정 — 제시값 그대로 채택합니다

```css
/* Light */
--shadow-overlay: 0 4px 12px rgb(26 54 93 / 10%), 0 16px 40px rgb(26 54 93 / 14%);
/* Dark */
--shadow-overlay: 0 8px 24px rgb(0 0 0 / 32%), 0 24px 64px rgb(0 0 0 / 24%);
```

`lv1`·`lv2`의 기존 관례(라이트는 네이비 틴트, 다크는 검정 / 라이트는 넓은 층이 진하고 다크는 가까운 층이 진함)를 정확히 따랐습니다.

## 단, 설명 한 줄이 실제와 반대입니다

「`--shadow-lv2`보다 한 단 넓고 **옅게**」로 적혀 있으나 실제 값은 **더 넓고 더 진합니다.**

| | 가까운 층 | 넓은 층 |
|---|---|---|
| Light `lv2` | `4px 8px` / **8%** | `12px 32px` / **12%** |
| Light `overlay` | `4px 12px` / **10%** | `16px 40px` / **14%** |

오버레이가 `lv2`보다 높은 고도이므로 **진해지는 것이 맞습니다.** `§5`에 올릴 때 설명만 **「한 단 넓고 진하게」**로 고쳐 주십시오. 그대로 적히면 나중에 이 문장을 근거로 값을 낮춥니다.

## 적용 순서 — 지켜 주십시오

`AccountMenu.css:115`가 현재 `box-shadow: var(--shadow-lv2)`를 씁니다. 다크 `lv2`를 먼저 `none`으로 바꾸면 **교체 전까지 다크에서 드롭다운 그림자가 사라집니다.**

1. `--shadow-overlay` 신설
2. `AccountMenu`를 `--shadow-overlay`로 교체
3. 다크 `--shadow-lv1`·`--shadow-lv2`를 `none`으로

## 함께 처리할 것

**⑴ 다크 그림자가 두 곳입니다** — `tokens.css:232-233`(`@media (prefers-color-scheme: dark)`)과 `248-249`(`[data-theme='dark']`). 한 곳만 지우면 시스템 다크와 수동 다크가 갈립니다.

**⑵ 주석도 함께 지우십시오** — `tokens.css:220-222`

> 어두운 바탕에서는 같은 그림자가 보이지 않는다 — **다크에서는 더 검고 진하게 준다.**

`§5:401`·`§5:851-852`와 정면으로 배치되는 문장이고, **이번 이탈이 이 주석대로 구현된 것입니다.** 값만 지우고 남기면 다시 되돌아갑니다.

**⑶ `§5`에 규정 한 줄 추가**

> 오버레이 면은 그림자와 테두리를 **함께** 쓴다. 그림자만으로 분리하지 않는다.

다크에서는 검은 그림자가 거의 보이지 않으므로 **실제 분리는 테두리와 표면색이 담당합니다.** 현재 테두리가 `AccountMenu` 소유(`AccountMenu.css:113`, `var(--borderWidth-default) solid var(--border-default)`)라, 다음에 모달·토스트를 만드는 사람이 그림자만 가져다 쓰면 **다크에서 분리가 사라지고 라이트에서는 멀쩡해 보입니다.**

## 철회 — 「하드코딩 hex 위반」은 제 오류였습니다

`§15:704`의 조문은 「**컴포넌트는** 토큰만 참조한다. 하드코딩 hex 금지」로 **컴포넌트를 묶는 규칙**이고, 정본 `§5:774-775`가 라이트 그림자를 이미 `rgba(26,54,93,...)`로 적고 있습니다. 토큰 정의부는 원래 값이 놓이는 자리입니다. **`§15` 조문을 고치라고 한 것도 철회합니다.**

`--shadow-tint` 토큰화는 **선택 사항**으로만 남깁니다 — 네이비가 여러 토큰에 리터럴로 반복돼 primary 조정 시 조용히 어긋날 수 있다는 유지보수 사안입니다. 급하지 않습니다.

「화면」은 PRD가 이미 쓰는 집안 어휘입니다(「모든 결과 화면 하단에」). 그대로 갑니다.

**본문** `LoginPage.tsx:122` `LoginFailurePage`의 문장을 기본값으로 올립니다.

> 잠시 후 다시 시도해 주세요. 문제가 계속되면 관리자에게 문의해 주십시오.

⚠️ **어미를 통일해 주십시오** — 한 문장에 「주세요」와 「주십시오」가 섞여 있습니다.

## 영역 실패(B) — 기본 제목을 두지 않습니다

**「불러오지 못했습니다」를 기본값으로 두지 않습니다.** 이미 코드가 더 나은 관례를 갖고 있습니다.

```
VoyageCiiForm.tsx:275  선박 목록을 불러오지 못했습니다
VoyageCiiForm.tsx:303  규제연도 목록을 불러오지 못했습니다
VoyageCiiForm.tsx:395  연료 목록을 불러오지 못했습니다
```

기본값이 생기면 그 기본값이 쓰이고, 주어를 붙여 둔 이 세 곳도 컴포넌트로 옮길 때 주어가 사라집니다. **B는 화면 일부만 실패한 자리라 사용자는 어느 부분이 실패했는지를 알아야 합니다.**

**문장이 아니라 대상 명사 하나를 받습니다.**

```tsx
<ErrorState subject="선박 목록" />   →  선박 목록을 불러오지 못했습니다
<ErrorState action="계산" />        →  계산에 실패했습니다
```

조사(을/를)는 받침 판정 헬퍼로 컴포넌트가 붙입니다. **개발자는 명사 하나만 넘기므로 올바른 쪽이 더 쉬운 길이 됩니다.**

| 갈래 | 패턴 | 해당 |
|---|---|---|
| 조회 실패 | `{대상}을/를 불러오지 못했습니다` | 선박 · 규제연도 · 연료 목록 |
| 처리 실패 | `{동작}에 실패했습니다` | 계산 · 비교 |

`1-1`에서 ③(계산 실패)을 B에 합쳤으므로 두 갈래가 필요합니다. **기존 호출부 두 곳(「계산에 실패했습니다」·「비교에 실패했습니다」)은 두 번째 패턴에 그대로 흡수되며 문구가 바뀌지 않습니다.**

# C · 문구 등재 — `PRD §6.4` 신설

## 전제 정정 — 이 규칙은 이미 깨져 있었습니다

`#613`이 닫은 **빈 상태 문구도 PRD에 없습니다.**

```
FleetDashboard.tsx:99
"등록된 선박이 없습니다. 선박을 등록하면 이 화면에서 선대 전체의

```

**에러 규격이 새로 만든 구멍이 아니라 빈 상태가 닫힐 때 이미 나 있던 구멍입니다.** 에러만 등재하면 빈 상태가 밖에 남아 위반이 그대로입니다.

현재 `§6.3`은 면책 고지 · 규제 용어 · 계정 존재 노출 금지 · 탈퇴 시 기록 보존 등 **문구 자체가 법적·제품적 결정인 것들**이고 표 아래에 근거가 붙어 있습니다. 여기에 기계적인 상태 문구를 섞으면 **「모든 행이 의도된 결정」이라는 이 표의 가치가 희석됩니다.**

## 확정

- **`PRD §6.4 「상태 문구」` 신설** — 로딩 · 빈 상태 · 에러의 기본 문구와 **패턴**을 한 표에. 위 B대로 가면 개별 문자열이 아니라 **패턴 두 줄**만 등재하면 됩니다
- **빈 상태 문구도 이번에 함께 등재** — `#613` 후속으로 따로 걸지 않습니다. 어차피 같은 개정입니다
- **`§13` 개정** — 「문구 원문은 ~~PRD §6.3~~ → **PRD §6**에 있다」

# D · `§5` radius · 테두리 · Light 그림자 — 셋 다 〔확정〕

문서와 코드를 직접 대조했습니다. **세 값 모두 일치하며 갈린 적이 없습니다.**

## radius 〔확정〕

```
--radius-badge: 4px   --radius-control: 8px   --radius-card: 12px
--radius-modal: 16px  --radius-pill: 999px
```

사용처 114곳(control 60 · card 34 · pill 15 · badge 5). v2.0에서 「작은 태그 6px → 배지 4px」로 근거를 적어 한 번 조정한 값입니다.

⚠️ **단서** — `--radius-modal`과 `--radius-tag`는 **사용처가 0**입니다. 모달이 아직 없습니다. 확정하되 **첫 모달에서 16px이 실물에 맞는지 한 번은 눈으로 보셔야 합니다.**

## 테두리 〔확정〕

`--borderWidth-default: 1px`. 정본 「기본 `1px solid border`」와 일치.

## Light 그림자 〔확정〕

정본 `§5:774-775`와 `tokens.css:224-225`가 **표기만 다르고 값이 같습니다** — `rgba(26,54,93,.05)` ↔ `rgb(26 54 93 / 5%)`.

다크를 `none`으로 확정해 놓고 라이트를 제안으로 두면 같은 축의 절반만 정해진 상태가 됩니다.

➜ **표기는 코드 쪽(`rgb(... / %)`)으로 정본을 맞춰 주십시오.** 값이 같은데 표기가 달라 diff로 일치 여부가 보이지 않습니다.

# E · `§5` 포커스 링 — 목록에서 빠져 있었고, 갈려 있습니다

「문서와 코드가 갈린 적은 없습니다」가 이 항목에서는 성립하지 않습니다.

| | Light | Dark |
|---|---|---|
| 정본 `§5` | `0 0 0 3px rgba(26,54,93,.25)` | `0 0 0 3px rgba(91,143,212,.35)` |
| 코드 | `0 0 0 3px color-mix(in srgb, var(--semantic-focus) 45%, transparent)` | 같은 식 |

색은 맞습니다 — `--semantic-focus`가 라이트 `#1a365d`, 다크 `#5b8fd4`이고 `#5b8fd4` = `rgb(91,143,212)`입니다. **갈린 것은 불투명도입니다. 25%→45%, 35%→45%.**

## 확정 — 코드 값으로 정본을 갱신합니다

**메커니즘이 더 낫습니다.** 정본은 두 값을 따로 박아뒀는데 코드는 `--semantic-focus` 하나로 테마를 따라갑니다. `§14`의 「다크 모드는 별도 링 색을 쓴다」를 자동으로 만족하고 고칠 곳이 한 곳입니다.

**불투명도도 45%로 둡니다.** 흰 배경 기준 링 대비가 25%는 약 1.6:1, 45%는 약 2.5:1로 추정됩니다.

> 정확히 말하면 `§14` 목표가 **WCAG 2.1 AA**라 포커스 표시의 3:1 요건(SC 2.4.11)은 **2.2 항목이므로 의무가 아닙니다.** 45%도 3:1에는 못 미칩니다. 의무 위반을 피하려는 것이 아니라 **더 잘 보이는 쪽이라서** 45%입니다. 위 수치는 추정값이니 팀 계산기로 확인해 주십시오.

이번에 판정하지 않으면 **`§16` 항목 2가 `§5` 안에 살아 있는 이탈을 품은 채 닫힙니다.** 다크 그림자와 같은 상황입니다.

# F · 〔확정〕/〔제안〕의 정의

`§0.2`가 **값의 소유를 Figma에 두고** 있어(「본 문서는 이름·의미·제약을, Figma는 값을 소유한다」) 지금 상태로는 〔확정〕이 「누가 정했나」로 읽힐 여지가 있습니다. `§5`에 정의를 박아 주십시오.

> 〔확정〕 — 값이 정해졌다. 바꾸려면 Figma 개정과 문서 갱신을 함께 거친다. **코드가 다르면 코드가 틀린 것이다.**
> 〔제안〕 — 아직 정해지지 않았다. **담당과 기한을 함께 적는다.**

값의 소유는 Figma에 두되 **코드는 어느 쪽에서도 값을 위임받은 적이 없다**는 점만 분명히 하는 것입니다. 다크 그림자도 포커스 링도 코드가 스스로 값을 정한 경우였습니다.

➜ 이로써 **`§5`에 〔제안〕으로 남는 값이 하나도 없고**, `§16` 항목 2(`919`행 「§5 값은 제안값」)를 닫을 수 있습니다.

## 개발이 제시한 네 값은 전부 경계 기준에 걸립니다

혼합 목록(70 · 60 · 50 · 40)이 **흰 글자 대비만 보고 만들어졌습니다.** 페이지 쪽으로 섞을수록 판이 페이지에 가까워지므로 **경계 대비는 반대로 나빠집니다.**

| 혼합 | 흰 글자 (≥4.5) | 판↔페이지 경계 (≥3) |
|---|---|---|
| 100% `#4a7cc0` | 4.25 ❌ | 4.44 ✅ |
| **85%** | 5.35 ✅ | 3.53 ✅ |
| **80%** | **5.80 ✅** | **3.26 ✅** |
| 70% | 6.82 ✅ | 2.77 ❌ |
| 60% | 8.04 ✅ | 2.35 ❌ |
| 50% | 9.57 ✅ | ~2.0 ❌ |
| 40% | 11.22 ✅ | 1.69 ❌ |
| 라이트값 `#1a365d` | 12.14 ✅ | 1.56 ❌ |

**두 기준을 동시에 만족하는 창은 약 78–88%입니다.** 「라이트 값 고정」과 「다크만 낮춤」이 양 끝에서 각각 실패하는 이유가 이것입니다.

## 확정

```css
/* Light */
--brand-gradient-from: var(--color-primary);        /* #1a365d · 흰 글자 12.14 */
--brand-gradient-to:   var(--color-primary-hover);  /* #1a3151 · 흰 글자 13.11 */

/* Dark */
--brand-gradient-from: color-mix(in srgb, var(--semantic-primary) 80%, var(--surface-page));
--brand-gradient-to:   color-mix(in srgb, var(--semantic-primary) 68%, var(--surface-page));
```

- 흰 글자 **5.80** · 판↔페이지 경계 **3.26**
- **새 hex 0개** — `3-1`의 원칙 유지. 저장소가 이미 쓰는 방식(`--color-primary-solid`)과 같은 수단
- `to`를 68%로 둔 것은 라이트의 `from`→`to` 방향(살짝 어두워짐)을 다크에서도 유지하기 위함. 그러데이션 폭을 더 주려면 60%까지 내려도 글자는 안전합니다
- ⚠️ **`from`은 78% 아래로 내리지 마십시오** — 판의 경계를 담당합니다

> 경계 3:1은 엄밀히는 AA 의무가 아닐 수 있습니다 — WCAG 1.4.11은 UI 컴포넌트와 의미를 지닌 도형에 적용되고 장식용 브랜드 판은 어느 쪽도 아닙니다. 다만 창이 넉넉하니 맞추지 않을 이유가 없고, 판이 안 떨어져 보이면 기준 이전에 잘못 보이는 화면입니다.

## 시안 색은 계속 유예합니다

`3-1`의 결정을 유지합니다. **시안 색을 지금 넣으면 Figma 대조가 이 화면의 크리티컬 패스로 올라옵니다** — `3-1`에서 피하려던 상황이고 지금은 화면이 막혀 있어 더 그렇습니다. 위 값은 새 hex가 없으므로 오늘 진행됩니다.

대신 **`#933`이 값만 갈아끼울 수 있도록 규칙을 확정합니다.**

> 다크 판 배경은 라이트 브랜드 색을 `--surface-page` 쪽으로 내려 얻는다. **흰 글자 ≥ 4.5, 판↔페이지 경계 ≥ 3**을 동시에 만족하는 비율을 쓴다.

값이 아니라 **도출 방법**을 확정하는 것이라, 라이트가 `#3573DC`로 바뀌어도 비율만 다시 계산하면 됩니다.

**임시값은 필요 없습니다.** `--color-danger-text` 선례는 확정값을 기다리는 동안의 우회였고, 지금은 확정값이 나왔습니다.

# H · 토큰 가드 — 해석된 색 기준으로 작성합니다

「테마 불변」 가드가 선언 문자열만 비교해 양쪽 다 `var(--color-primary)`라 통과했습니다. **이건 개별 실수가 아니라 가드 설계의 문제입니다** — 별칭을 문자열로 비교하면 **별칭 아래의 갈라짐은 원리적으로 안 잡힙니다.** 이번엔 두 겹(`--brand-*` → `--color-primary` → `--semantic-primary`)이었고 세 겹이면 또 놓칩니다.

**9/10 문서에서 지시한 가드 셋이 전부 같은 함정 위에 있습니다.**

| 가드 | 출처 | 문자열 비교 시 뚫리는 경로 |
|---|---|---|
| 에러 표현에 `--cii-*`를 쓰지 않는다 | `1-3` | `--cii-e-bg`를 가리키는 별칭을 쓰면 통과 |
| 모든 문자 토큰 × 표면 대비 검사 | `2-1` | 토큰이 `color-mix`면 문자열로는 색을 못 구함 |
| 브랜드 판 테마 규칙 | `3-4` | 이번 건 |

**세 가드 모두 선언 문자열이 아니라 해석된 최종 색을 기준으로 작성하십시오.** `getComputedStyle`로 실제 렌더 값을 받거나 토큰 그래프를 끝까지 펼쳐 해석해야 합니다. **이 저장소는 `color-mix`를 여러 곳에서 쓰고 있어 문자열 비교로는 처음부터 성립하지 않습니다.**

# J · `2-10` 등급 전이 — `§8.3` 신설

## `§0.2` 제약 2가 답을 정해 줍니다

제약 2의 네 번째 조건:

> 두 체계를 **같은 컴포넌트 안에서 동시에 색으로 쓰지 않는다**

`C → B`를 그리면 `GradeBadge` 두 개가 이미 **등급 색**을 씁니다. 여기에 화살표를 「개선이니 Success 초록」으로 칠하면 **한 컴포넌트 안에 등급 색과 시맨틱 색이 동시에 들어가 제약 2 위반**입니다.

그리고 `§8`이 같은 판단을 이미 두 번 했습니다 — `DataConfidenceBadge`(`§8`)와 `ApplicabilityBadge`(`§8.2`) 모두 「`GradeBadge` 옆에 놓이므로 **등급 색을 쓰지 않는다**」. 전이 연결자도 같은 자리입니다.

## 확정

- **새 컴포넌트를 만들지 않습니다.** 기존 `GradeBadge` 두 개를 나열하고 사이에 연결자를 둡니다
- **연결자는 중립색입니다.** 등급 색도 시맨틱 색도 쓰지 않습니다
- **개선·악화를 색으로 말하지 않습니다.** `C`와 `B`라는 문자가 이미 말하고, 하단 비교는 「조정 전 / 조정 후」 행 라벨이 방향을 말합니다
- ⚠️ **`§4.3`(▼▲ + 부호)을 끌어오지 마십시오.** 그것은 수치 증감용이고 등급은 수치가 아닙니다. 붙이면 등급 배지 옆에 시맨틱 색이 다시 들어옵니다
- **변화가 없으면 전이를 그리지 않고 배지 하나만 둡니다.** `§8.2`의 「해당일 때 그리지 않는다」와 같은 계열입니다 — 바뀌지 않은 것에 화살표를 그리면 바뀐 행과 구분되지 않습니다

> 마지막 항목은 원 질의에 없던 자리입니다. `C → C`의 표현이 정해지지 않은 채로 두면 구현이 임의로 채웁니다.

# 9/10 확정 문서 정정 — 둘

## ⑴ `3-4` 「테마 불변」은 잘못된 결정이었습니다

## ⑵ `--color-primary-hover`의 값이 오기였습니다

```css
--color-primary-hover: color-mix(in srgb, var(--semantic-primary) 82%, var(--text-primary));
```
